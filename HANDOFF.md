## Проверка стопа — ЗАКРЫТА и подтверждена живой сделкой (10.08)

`demo-fapi` по-прежнему не отдаёт список условных ордеров, но отвечает на запрос по имени. Замерено
прямо по эндпоинту, не по документации:

| запрос | ответ |
|---|---|
| `GET /fapi/v1/algoOpenOrders?symbol=…` | `404 -5000 Path … is invalid` — списка нет |
| `GET /fapi/v1/algoOrder?clientAlgoId=<несуществующий>` | `400 -2013 Order does not exist` |

`-2013` — это `BinanceErrorCodes.NO_SUCH_ORDER`, то есть «нет ордера» отличимо от «эндпоинт сломан».
На этом и построено: `ExposureBook.OpenPosition` носит `protectiveStopId`, `RiskEngine.registerFill`
требует его (позицию нельзя записать, не назвав её стоп), Reconciler переносит id между проходами и
спрашивает биржу поимённо. Стоп рабочий → сходится и заодно проверяется буфер ликвидации; отменён,
истёк или неизвестен бирже → `POSITION_WITHOUT_STOP` и стоп торговли.

Три случая молчат намеренно, потому что алерт на здоровой позиции приучает игнорировать все алерты:
id нет в записи (позиция подхвачена с биржи), запрос не прошёл (сеть), статус в незнакомых словах.
Сработавший стоп получает **ровно один** проход форы — обычный стоп-аут не должен поднимать тревогу,
но триггер, за которым не пришло закрытие, через проход становится дефектом.

**Проверено живой сделкой** (ETHUSDT LONG 0.651 @ 1908.88, строка очереди 10):

- рабочий стоп по имени читается — `algoStatus:"NEW"`, `orderType:"STOP_MARKET"`,
  `triggerPrice:"1870.26"`, `reduceOnly:true`, `closePosition:true`, `quantity:"0.000"`.
  Поля ровно те, что ждёт `parseAlgoOrder`; `quantity=0` при `closePosition=true` — норма, стоп
  сверяется по типу и триггеру, не по объёму;
- 5 проходов сверки прошли молча, старое «cannot confirm its stop» из лога исчезло;
- стоп снят у бота за спиной → следующий проход: `POSITION_WITHOUT_STOP on ETHUSDT`, halt, критический
  алерт. То есть тревога не только не ложная, но и реально срабатывает;
- закрытие reduce-only отработало: 0.651 @ 1910.30, `close_price` записан (не 0 — фикс держится).
