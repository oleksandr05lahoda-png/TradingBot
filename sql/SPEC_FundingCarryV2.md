# FundingCarryV2 — исполняемая спецификация

Назначение: воспроизвести в SQL ровно то, что считает Java-стенд, чтобы форвард и бэктест
были сравнимы числом. Составлено чтением кода
(`FundingCarryV2.java`, `CarryPaperExecutor.java`, `CarryPosition.java`), не по памяти.

Версия гипотезы `v2` заморожена. Пороги не подлежат изменению.

## 0. Константы и сетка

| Имя | Значение |
|---|---|
| `BAR_MS` | `14400000` (4 часа) |
| `ENTRY_FUNDING` | `0.0005` |
| `EXIT_FUNDING` | `0.0`, сравнение **строгое** (`<`) |
| `EXIT_BASIS_BP` | `0.0` |
| `HOLD_BARS` | `114` (57 расчётов × 8ч = 456ч) |
| `TAKER_FEE` | `0.0005` за одно исполнение |
| `FILLS` | `4` → `fees = 0.0020` всегда |
| `SLIP` | `0.0002` (2 б.п.) за одно исполнение |

Бар задаётся `open_ms = klines_4h.ts_ms`, и **по определению**

```
close_ms = open_ms + BAR_MS
```

Конец **исключающий**: закрытие бара A и открытие бара B имеют одну метку времени.
Это конвенция стенда, от неё зависят все граничные правила ниже.

Ноги: перп — `klines_4h`, спот-прокси — `index_klines_4h`. Бар одной ноги соответствует бару
другой **только при равенстве `ts_ms`**. Ближайший по времени не подходит.

---

## 1. Условие входа

Оценка проводится на закрытии каждого бара. Пусть `B` — бар, только что закрывшийся,
`asOf = B.close_ms`.

**1.1. Обе ноги обязаны быть.** Существуют бары перпа и спота с одинаковым `ts_ms`, и это
последние бары, закрывшиеся к `asOf`. Если у любой ноги бара нет — символ пропускается.

**1.2. Ряд расчётов.** Берутся строки `funding_history` символа с `funding_time_ms <= asOf`,
упорядоченные по `funding_time_ms`. Требуется **не менее двух** строк, иначе пропуск.

- `last` — строка с наибольшим `funding_time_ms` в этом наборе
- `prev` — **непосредственно предыдущая строка в этом же упорядочении**

**Что при пропуске расчёта.** `prev` — это предыдущая *имеющаяся* строка, а не «строка на 8 часов
раньше». Если расчёт в базе отсутствует, `prev` окажется на 16 или более часов раньше, и это
считается корректным поведением. В SQL это в точности
`lag(funding_rate) over (partition by symbol order by funding_time_ms)`.

**1.3. Расчёт произошёл внутри этого бара** (полуоткрытое окно):

```
last.funding_time_ms >  B.open_ms
last.funding_time_ms <= B.close_ms
```

**1.4. Пересечение порога снизу:**

```
last.funding_rate >  0.0005
prev.funding_rate <= 0.0005
```

Обратите внимание на асимметрию сравнений: вход требует **строго больше** порога, а предыдущее
значение — **не больше**. Ставка ровно `0.0005` входа не даёт.

**1.5. Событие, а не состояние.** Условие 1.3 гарантирует, что позиция открывается только на том
баре, внутри которого произошёл переход. Пока ставка остаётся высокой, новые позиции не
открываются — один эпизод даёт одну позицию.

При выполнении 1.1–1.4 фиксируется `signal_bar_close_ms = B.close_ms`.

## 2. Бар входа и цены входа

**2.1.** Бар входа — первый бар перпа с `open_ms >= signal_bar_close_ms`. При непрерывной сетке
это бар, открывающийся ровно в `signal_bar_close_ms`.

**2.2. Отказ при разрыве ряда.** Если

```
entry_bar.open_ms - signal_bar_close_ms >= BAR_MS
```

— **сделки нет**. Такое происходит при дыре в данных: вход пришёлся бы на бар часами позже, по
цене, которой решение не видело.

**2.3.** Бар спота с тем же `open_ms` обязан существовать, иначе **сделки нет** (хеджа нет).

**2.4. Цены входа.** Проскальзывание против нас на обеих ногах:

```
perp_entry_px = perp_bar.open * (1 - SLIP)     -- шорт продаёт ниже
spot_entry_px = spot_bar.open * (1 + SLIP)     -- лонг покупает выше
```

**2.5. Базис входа** считается по **сырым** ценам, без проскальзывания:

```
basis_entry_bp = (perp_bar.open - spot_bar.open) / spot_bar.open * 10000
```

---

## 3. Условия выхода и порядок проверки

Сканируются бары с индексами `entryIdx .. entryIdx + HOLD_BARS - 1` включительно.
**Бар входа входит в диапазон** — позиция может закрыться на том же баре, на котором открылась.

Для каждого бара `P` (перп):

**3.0.** Найти бар спота `S` с тем же `open_ms`. **Если его нет — бар пропускается** (`continue`),
сканирование продолжается. Это не отказ и не выход.

**3.1. Сначала funding.** Если существует расчёт с

```
f.funding_time_ms >  P.open_ms
f.funding_time_ms <= P.close_ms
f.funding_rate    <  0.0        -- СТРОГО меньше нуля
```

→ выход `funding_flipped` по **ценам закрытия** `P.close` и `S.close`.

Строгость существенна: 1452 расчёта из 129238 в dev-периоде равны ровно нулю. Нулевая ставка не
платит ничего ни в одну сторону, поэтому позицию не закрывает.

**3.2. Затем базис.** Если

```
(P.close - S.close) / S.close * 10000 <= 0.0
```

→ выход `basis_converged` по **ценам закрытия** `P.close` и `S.close`.

**3.3. Порядок при одновременном срабатывании.** В пределах одного бара **funding проверяется
первым и выигрывает**. Если на одном баре выполняются оба условия, причина выхода —
`funding_flipped`.

**3.4. Тайм-стоп.** Если за весь диапазон ни одно условие не сработало, выход происходит на баре
с индексом `entryIdx + HOLD_BARS` по **ценам открытия** `P.open` и `S.open`.

Если этого бара нет или у него нет парного бара спота — **эпизод остаётся неразрешённым и не
записывается**. Выдумывать исход нельзя.

## 4. Расчёт `ret_gross` по четырём ценам

**4.1. Цены выхода** — проскальзывание снова против нас:

```
perp_exit_px = perp_exit_raw * (1 + SLIP)      -- откупаем дороже
spot_exit_px = spot_exit_raw * (1 - SLIP)      -- продаём дешевле
```

где `*_raw` — это `close` при выходах 3.1/3.2 и `open` при тайм-стопе 3.4.

**4.2. Ноги считаются раздельно, каждая к СВОЕЙ цене входа:**

```
perp_leg = (perp_entry_px - perp_exit_px) / perp_entry_px      -- шорт зарабатывает на падении
spot_leg = (spot_exit_px  - spot_entry_px) / spot_entry_px      -- лонг зарабатывает на росте
ret_gross = perp_leg + spot_leg
```

**Не** через дрейф базиса. Приближение `-(b1 - b0)` отбрасывает член порядка `r·b1`; при росте
спота 5% и выходном базисе 5 б.п. это 0.25 б.п. — пять процентов измеряемого сигнала.

**4.3. Базис выхода** — по сырым ценам выхода, для диагностики:

```
basis_exit_bp = (perp_exit_raw - spot_exit_raw) / spot_exit_raw * 10000
```

## 5. Funding, комиссии, итог

**5.1. Атрибуция расчётов.** Суммируются расчёты в полуоткрытом окне

```
f.funding_time_ms >  entry_bar.open_ms
f.funding_time_ms <= exit_bar.close_ms
```

Начало **исключающее**: расчёт ровно на открытии бара входа накопился до того, как позиция
существовала. Конец **включающий**: расчёт на границе принадлежит бару, над которым он накопился.
Binance расчитывает в 00:00/08:00/16:00 UTC, то есть ровно на границах 4h-баров — правило
затрагивает реальные случаи, а не угловые.

**5.2. Знак.** Шорт перпа **получает** положительную ставку. Хранится как **расход**:

```
funding = - sum(f.funding_rate)
```

Собирающая позиция даёт отрицательное `funding`. Спотовая нога funding не имеет.

**5.3. Комиссии** — плоская величина, к ценам не применяется:

```
fees = 4 * 0.0005 = 0.0020
```

Четыре исполнения: открыть шорт перпа, открыть лонг спота, закрыть обе.

**5.4. Итог:**

```
ret_net = ret_gross - fees - funding
```

Проверяется построчно; на dev-прогоне v2 нарушений 0 из 1061.

## 6. ИЗВЕСТНОЕ РАСХОЖДЕНИЕ — решить до запуска форварда

При выходе по тайм-стопу (3.4) цена выхода берётся по **открытию** бара, а окно начисления
funding (5.1) тянется до **закрытия** того же бара. Позиция кредитуется четырьмя лишними часами
funding относительно момента, когда она фактически закрыта.

Измерено на dev-прогоне v2: из 84 эпизодов `time_stop` лишний расчёт попадает в хвост у **22**,
средняя лишняя величина по группе **+0.0057%**. Вклад в общее среднее ≈ `84/1061 × 0.0057% ≈
0.0005%` — на вывод не влияет (среднее `+0.6535%`, помесячный `t = 1.45`).

Но для сравнимости форварда и бэктеста это надо решить **одинаково в обеих реализациях**:

- **Вариант 1, предпочтительный:** окно заканчивается там же, где берётся цена. Для тайм-стопа
  конец окна `exit_bar.open_ms`, для выходов 3.1/3.2 — `exit_bar.close_ms`.
- **Вариант 2:** оставить как есть, зафиксировав это как сознательное соглашение.

Пока решение не принято, SQL-версия должна повторять текущее поведение (`exit_bar.close_ms`
во всех случаях), иначе числа разойдутся.
